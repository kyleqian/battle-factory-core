# Bootstrap v3 — canonical Battle Factory anchor

`bootstrap/factory.json` (version 3) is the canonical anchor every trace run
starts from:

> **Inside the Level-50 SINGLE Battle Factory challenge, on the rental-mon
> draft screen ("Select the first POKéMON."), open and interactive: cursor on
> rental slot 1 of 6, no mon selected, no dialogue printing.** The player
> object is parked in `BattleFrontier_BattleFactoryPreBattleRoom` (mapGroup=26,
> mapNum=32) at (8,8) underneath the draft UI. The challenge has been entered
> for real: LEVEL 50, SINGLE mode, the pre-challenge save already answered YES
> (the flash write is ephemeral — see below).

- **Total frames: 6970** (6910 scripted-input frames + 60 `settleFrames`).
  Inputs only — `pokes` is empty.
- **Canonical screen sha256** (raw RGB888 framebuffer, not PNG):
  `9c89c74113f29e7d4595571c3aceb728417c4fe441b644ec0022fb498463f297`
- **Pinned rental pool** (slots 1-6, read off the draft screen by stepping the
  cursor RIGHT): **ONIX, MAGBY, BAYLEEF, BUTTERFREE, HAUNTER, QUILAVA.**
  The pool is generated by `factory_generaterentalmons` from the RNG state at
  arrival, so it is a function of the exact input timeline: any change to any
  earlier segment (even idle counts) reshuffles it. The v3 timeline pins this
  one pool (and one first opponent — the attendant's scouting report for it:
  "apparently skilled in the handling of the FLYING type", "favorite battle
  style appears to be weakening the foe to start").

## Save provenance

`bootstrap/factory.sav` (sha1 `93186502aabf5ae699a5f90e6acc0e2ec15143ea`) is a
raw 128 KiB GBA battery save converted on 2026-07-16 from the GameFAQs
SharkPortSave export `pokemon-ruby-sapphire-emerald-version.34461.sps`
(GameFAQs save id 34461, from Kyle's Desktop) with
`bootstrap/convert-sps.py`. It is a post-game file: player `MEMORY`, 386 dex,
8 badges, `FLAG_SYS_GAME_CLEAR` set, saved inside the **Battle Frontier
Pokémon Center 1F** (map 26.53) at (10,3).

`emerald_core.py` loads it **read-only** via mGBA's `load_temporary_save` —
the emulator works on an in-memory copy and never writes back, so the vendored
`.sav` stays pristine no matter what a trace run does. **This makes the v3
save prompt safe:** the challenge-entry flow answers YES to the game's "I need
to save the game" sequence and the emulated flash write really happens, but
only in the in-memory copy. It is ephemeral, deterministic, and replayed
identically on every boot; `factory.sav` on disk never changes.

## What the script does

**v1 prefix (frames 0–1379): power-on → CONTINUE → free-roam in the Pokémon
Center.** 800 idle frames (unskippable copyright/logo), A (skip intro movie),
START, START, A (select CONTINUE on the main menu), 300 idle frames for the
fade into the overworld, then 60 idle frames (v1's former `settleFrames`, kept
as an explicit segment so v2 replays v1's canonical state exactly). Player
stands at (10,3) in map 26.53.

**v2 route (frames 1380–3933): walk to the Factory attendant.** Every leg was
verified during authoring with a screenshot plus a SaveBlock1 (x,y,group,num)

alone is not sufficient (door tiles read as solid; ledges read as passable).

**Frames 3934–3993: v2's former `settleFrames`,** kept as an explicit 60-frame
idle segment so the v3 additions replay on top of the exact v2 canonical
state (screen sha at frame 3993 is v2's canonical
`ebb6ad29cc122f04c1e64217774c784f403d821154fec407cb0166371d44874d`).

## How the script was authored

Iterated with throwaway probes that instantiate `EmeraldOracle` in-process (no
server), drive frames with `o.advance(buttons)`, dump PNGs at checkpoints, and
read SaveBlock1 between legs. Screenshots were ground truth at every stage.
Mechanics that mattered:

- Movement granularity (same as the littleroot bootstrap): with the player
  already facing a direction, an 8-frame held tap + 16 released frames walks
  exactly one tile; a 4-frame tap turns in place when not already facing that
  way but WALKS if already facing it.
- Doors: exterior door tiles are solid in the collision grid — walking into
  them (one more directional press from the tile in front) triggers the
  animated-door warp. Exiting a building auto-steps the player one tile out of
  the door during the door animation (PC exit lands at (3,52), not the warp
  tile (3,51)); budget ~200 idle frames for exit, ~250 for entry.
- Outside East/West are seamlessly connected (offset 0); crossing updates
  mapNum without a warp fade.
- Wandering NPCs (lobby woman at (3,11), plaza wanderers) can bump a recorded
  run off its tile count; the route stays 2+ tiles clear of their wander
  ranges. Replay determinism makes NPC motion identical every run, so a route
  verified once holds forever.

v3-specific mechanics:

- Scout the real event scripts first: the whole prompt chain (which menus
  appear, which option index each case handles, which yes/no default applies)
  is readable in `data/maps/BattleFrontier_BattleFactoryLobby/scripts.inc`,
  `src/data/script_menu.h`, and `src/start_menu.c` of the pokeemerald
  checkout. Screenshots then confirm each landing.
- "MEMORY saved the game." does **not** wait for input in this scripted save
  (the script resumes and replaces it with "Please step this way."), so the
  save step needs one long idle (700 frames covers the emulated flash write
  with margin), not an extra A-tap.
- The rental pool / opponent are RNG-derived at walk-in. Touching any earlier
  frame count reshuffles them — treat the whole segment list as pinned once
  verified, and re-record the pool if you ever change anything upstream.
- A `pos()` read of (8,13)→(8,8) 26.32 confirms the warp + walk-in landed;
  the draft screen itself doesn't change SaveBlock1 position.

## How to re-verify / extend

Fresh-process pattern (run TWICE and diff for determinism). Use the venv
python: `../../vendor/mgba-venv/bin/python`.

```python
import sys, hashlib
sys.path.insert(0, "../pokeemerald-factory/oracle")
from emerald_core import EmeraldOracle
o = EmeraldOracle(
    rom_path="../../vendor/pokeemerald/pokeemerald.gba",
    map_path="../../vendor/pokeemerald/pokeemerald.map",
    bootstrap_path="../pokeemerald-factory/oracle/bootstrap/factory.json",
)
print(o._bootstrap_frames, o.canonical_screen_sha256)  # 6970 9c89c741...
def pos():
    sb1 = o.read_u32(o.symbols["gSaveBlock1Ptr"])      # re-deref EVERY read
    return [o.read_u8(sb1 + i) for i in range(6)]
print(pos())                                            # [8, 0, 8, 0, 26, 32]
# movement smoke test: RIGHT moves the draft cursor to slot 2 (MAGBY)
o.new_session()
for _ in range(6): o.advance(["RIGHT"])
for _ in range(20): o.advance([])
print(hashlib.sha256(o.screen_rgb()).hexdigest())
# f98116c078fce6458b46917d833dd2a52ec904a307c7252aed034872ba047f1b
```

(The process may segfault at interpreter exit inside libmgba-py teardown —
harmless, but flush your output before returning.)

To extend the anchor (e.g. rent the three mons and step to the first battle),
append segments to the JSON and re-run the two-process check; keep screenshots
as acceptance evidence and never let `description` claim more than a
screenshot proves. Remember any upstream frame change reshuffles the rental
pool — re-verify and re-document it.

Note: the server on port 8012 snapshots its bootstrap at startup — restart it
(outside this doc's scope) to pick up a version bump — and keep
`oracle/smoke-test.py`'s `BOOTSTRAP_VERSION` pin in lockstep (bumped to 4
with the v4 change below; the anchor sha pin is unchanged by design).

## Dual Battle Scene profiles (2026-07-23)

The harness now exposes two simultaneous deterministic oracle profiles:

- `battle-scene-on` on port 8012 uses `bootstrap/factory.json` and remains
  the immutable reference for all existing animation-on traces.
- `battle-scene-off` on port 8014 uses
  `bootstrap/factory-battle-scene-off.json`. It inherits the exact same save,
  input timeline, and settle frames, then sets `optionsBattleSceneOff` with a
  zero-frame RAM poke before settling. The draft anchor, rentals, and RNG are
  therefore identical; only battle presentation takes the real game's OFF
  branches.

Run them independently with `./run-oracle.sh --profile battle-scene-on` and
`./run-oracle.sh --profile battle-scene-off`. Main round-loop work uses OFF;
the dedicated animation workstream and all legacy traces use ON.

## v5 — Battle Scene ON moved into the save file itself (2026-07-18)

Same user decision as v4, cleaner mechanism (user preference: no runtime
manipulation): `bootstrap/set-battle-scene-on.py` (committed, idempotent,
re-runnable) edits `factory.sav` at rest — SaveBlock2 options hi byte
`0x07 → 0x03` (clears `optionsBattleSceneOff`, u16 bit 10; sound/battle-
style bits preserved) in both save slots' SaveBlock2 sectors (sector 2,
counter 3726 and sector 15, counter 3725), recomputing each sector's
checksum (algorithm + layout from `reference/pokeemerald/src/save.c`; the
per-sector used size 0xefc was re-derived from the file by finding where
the stored checksum verifies, not hard-coded). The `pokes` array is empty
again. The pristine .sav is recoverable via git history.

Verified 2026-07-18: fresh-bootstrap probe reads `optionsBattleSceneOff=0`
with the anchor framebuffer sha byte-identical (`9c89c741…`); smoke test
green (`BOOTSTRAP_VERSION = 5`); the warm-bison turn-1 groundtruth replay
is **byte-identical to v4's** (223/223 capture shas) — v5 ≡ v4 in ground
truth, only the mechanism differs; full 19-trace sweep matches the v4
sweep exactly.

## v4 — Battle Scene (move animations) forced ON (2026-07-18, user decision) [superseded by v5]

The imported save carried **Options → Battle Scene: OFF**
(`gSaveBlock2Ptr->optionsBattleSceneOff == 1`), which sets
`HITMARKER_NO_ANIMATIONS` at every battle init (`battle_main.c:3084-3086`)
and suppresses every move's custom animation (`Cmd_attackanimation`) plus
the mon front-sprite entrance animation after send-out
(`BattleAnimateFrontSprite`'s `SKIP_FRONT_ANIM`, `pokemon.c:6888`). Per an
explicit user scope decision (2026-07-18, warm-bison supervisor session),
v4 forces the option ON **without touching the input timeline**: a single
entry in the bootstrap's previously-unused `pokes` field (applied after all
scripted segments, before the 60 settle frames — zero added frames, zero
RNG impact):

- poke: `gSaveBlock2Ptr` (deref) + 0x15 → byte `0x03` (was `0x07`) —
  clears u16 bit 10 (`optionsBattleSceneOff`) of the options word at
  SaveBlock2+0x14; the sound (STEREO) and battle-style (SET) bits are
  preserved. Resolved pointer at the anchor: `0x2024a54` (deterministic).
- Verified 2026-07-18: anchor framebuffer sha **unchanged**
  (`9c89c741…`, byte-identical to v3 — the option isn't rendered);
  smoke-test golden hashes all pass; in-battle
  `optionsBattleSceneOff` reads 0; replaying the warm-bison run's
  turn-1 groundtruth trace shows animations playing (first divergence
  from v3 truth at tick 1968, 172 of 223 captures differ, all
  pre-battle captures byte-identical).
- A latent harness bug was fixed to make pokes work at all:
  `emerald_core.write_u8` used libmgba-py's broken `u8.__setitem__`
  sugar (3 args to a 4-arg raw writer); it now calls
  `memory.u8.raw_write` directly. The pokes path had never been
  exercised before v4.
- Downstream: any run's ground truth captured in a battle window under
  v3 (move animations suppressed) is stale by design and must be
  re-captured; pre-battle/draft/intro windows up to each battle's
  send-out settle are byte-identical (empirically re-verified across
  warm-bison's full 19-trace suite — only send-out-and-later windows
  moved).

## Pre-report anchor (`bootstrap/factory-pre-report.json`, 2026-07-30)

A second, earlier canonical snapshot — not a replacement for the anchor
above, which every shared oracle server process still boots from
unchanged. **Do not point `POKEBENCH_ORACLE_BOOTSTRAP` at this file for a
normal server process** — `prepare()` assumes the anchor above and will
fail loudly (`RuntimeError: battle lab route did not reach the player
action menu`, confirmed live) rather than silently misbehave, but there's
no reason to hit that. It exists because Battle Lab's
`DoBattleFactorySelectScreen` re-entry point (used by `prepare()`) is
chronologically *after* the attendant's scouting-report dialogue already
printed for the one fixed opponent this file's `segments` bake in; there
was no way to get real ROM footage of that dialogue, or of the
rental-selection/intro window itself, for anything other than that one
fixed case.

**Derivation:** a literal truncation of this file's own `segments[0:193]`
— the v1 (power-on → overworld) plus v2 (walk to the attendant) prefix,
reused byte-for-byte, not re-authored. `settleFrames` is 0 because
segment 192 already is the explicit 60-frame settle v3 later builds on
top of (see "What the script does" above). Total: 3994 frames.

**Verified 2026-07-30**, three independent fresh processes (the venv
python, `EmeraldOracle` instantiated directly against the new file):
canonical screen sha256 **`ebb6ad29cc122f04c1e64217774c784f403d821154fec407cb0166371d44874d`**
and `SaveBlock1` position `(4, 8)`, map `26.31` — both match this
document's own already-published v2 checkpoint values exactly (the
"How the script was authored" v3 table above; this is independent
corroboration, not just self-consistency, since those values were
recorded in a different authoring session).

**Why a new anchor and not a mid-script poke:** the safe-looking gap
between the source's `factory_generateopponentmons` (writes
`gFrontierTempParty`) and `factory_getopponentmontype`/
`factory_getopponentstyle` (read it to compute the report) turned out not
to be reachable at frame granularity — both special commands, and the RNG
rolls before them, run inside the same single emulated video frame with no
blocking script command in between. A live probe confirmed this directly:
poking `gFrontierTempParty` to a different real opponent the instant a
frame-level `advance()` showed the transition to the default opponent's
data left the computed report values unchanged from an unpoked baseline.

**Correction (a later adversarial review):** the reason is narrower than
first stated here — it is not that no gap exists. Single-CPU-instruction
stepping (`mgba.core.Core.step()`, vendored but unused anywhere in this
codebase's frame-level `advance()` API) shows the write to
`gFrontierTempParty` and the reads that compute the report are actually
several thousand CPU instructions apart, still inside that one video
frame. Frame-level control genuinely cannot reach a gap that's *inside* a
frame, not because the gap is zero-width, but because `advance()` only
exposes state *between* whole frames, and both the write and the read
finish before the frame it's part of ever returns control. A one-shot poke
at that instruction-level gap does not simply work either: source review
confirms `GenerateOpponentMons` writes `gFrontierTempParty`'s three slots
in a loop, so poking only the first slot's write gets overwritten moments
later by the same function's own remaining iterations (confirmed live:
one poked slot stuck, the other two reverted to the original values). A
poke held continuously across the whole frame, re-applied every step,
does change the computed report — proving the underlying limit here is
this codebase's frame-granularity tooling, not the ROM itself. Nothing in
`preview_report()`'s shipped implementation uses instruction-level
control — it only calls `advance()` — so this doesn't change what the
method can do today, but a more capable, unexplored implementation using
the debugger primitives already vendored in `libmgba-py`
(`mgba.debugger.NativeDebugger`) could plausibly reach real opponent
selection in the future.

**What does work:** `gRngValue`, poked immediately after `new_session()`
— tens of frames before generation runs, not competing with it — changes
the seed the whole generate-then-describe sequence reads at its start.
This cannot choose a specific opponent, only a seed; different seeds
were verified to produce different real opponents and different real,
ROM-computed report values (`BattleLab.preview_report()`,
`oracle/report-preview-smoke-test.py`, four seeds including the default).
The same seed reproduces the same opponent and report.

`BattleLab.preview_report()` in `battle_lab.py` is the only consumer;
it requires its `EmeraldOracle` to be constructed against this bootstrap
file specifically (`bootstrap_path=.../factory-pre-report.json`), not
the shared server's default anchor — see its docstring and
`oracle/report-preview-smoke-test.py` for the in-process usage pattern
and full live verification.
