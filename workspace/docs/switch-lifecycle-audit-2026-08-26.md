## §0. The three distinct switch machines this audit must not conflate

Reading the port, three code paths converge on the *same* switch-in chain, and each enters it from a different place:

1. **Voluntary switch (the action).** `HandleAction_Switch` (`battle_util.c:294-311`) → `BattleScript_ActionSwitch` (`data/battle_scripts_1.s:3088-3121`). Runs as a whole turn *action*, `gCurrentMove` is `MOVE_NONE`. This is the §1/§2/§4 spine. Port: `factoryBattleScriptFullTurnDecision.ts:1710` `runVoluntarySwitchAction`.
2. **Forced switch (Roar/Whirlwind, and Baton Pass).** `Cmd_forcerandomswitch` (`battle_script_commands.c:7185`) and `EFFECT_BATON_PASS`'s `openpartyscreen` both run *inside* a move's script, so `gCurrentMove` is a real move — which is exactly the discriminator `SwitchInClearSetData` reads at `battle_main.c:3158`/`:3173`/`:3210`. §5.
3. **Faint replacement.** `HandleFaintedMonActions` → `BattleScript_FaintedMonChooseAnother`. **Out of scope** (sibling audit), but it matters here because it is the *only* one of the three that calls `FaintClearSetData` (`battle_main.c:3264`) instead of `SwitchInClearSetData` — `FaintClearSetData` additionally clears the whole of `gProtectStructs[battler]` (`:3292-3310`), which `SwitchInClearSetData` never touches. That asymmetry produces one of §3's findings.

The single most load-bearing fact for §3: **`SwitchInClearSetData` lives in `battle_main.c:3152-3262`, not `battle_util.c`.** A one-file grep of `battle_util.c` returns nothing and silently invites a false DIVERGENT.

Second load-bearing fact: `rg` over `reference/` returns **zero hits** (symlink). Every source cite in this doc was taken from `$(cd reference/pokeemerald && pwd -P)` = `../../vendor/pokeemerald`.

## §1. Where a switch action sits in turn order

`SetActionsAndBattlersTurnOrder` (`battle_main.c:4756-4850`) builds `gBattlerByTurnOrder` / `gActionsByTurnOrder` in **three passes**:

```
pass A  :4817-4825   every battler whose action is B_ACTION_USE_ITEM or B_ACTION_SWITCH,
                     in ASCENDING BATTLER INDEX order
pass B  :4826-4834   every other battler, ascending battler index
pass C  :4835-4850   bubble sort with GetWhoStrikesFirst(b1, b2, FALSE),
                     SKIPPED for any pair where either slot is USE_ITEM or SWITCH  (:4841-4844)
```

So a switch is not "priority +6": it is *removed from the speed comparison entirely* and parked at the front in index order. Two consequences that a naive port gets wrong:

* **Both sides switching the same turn** → battler 0 (player) resolves first, battler 1 (opponent) second, **regardless of speed**, deterministically.
* **`GetWhoStrikesFirst` is never called for a pair involving a switch**, so the speed-tie `Random() & 1` at `battle_main.c:4728` / `:4745` is **not drawn**. One switch action in a turn removes one potential RNG draw from that turn's stream.

### DIVERGENT summary

**D1 — Pursuit's ×2 switch-interception multiplier is dropped (high).**
* Source: `data/battle_scripts_1.s:3091` `setbyte sDMG_MULTIPLIER, 2`, inside `BattleScript_ActionSwitch`'s prelude. `sDMG_MULTIPLIER` is `gBattleScripting.dmgMultiplier` (`include/constants/battle_script_commands.h:261`), consumed by `Cmd_damagecalc` at `battle_script_commands.c:1296` as `gBattleMoveDamage = gBattleMoveDamage * gCritMultiplier * gBattleScripting.dmgMultiplier`. `BattleScript_PursuitDmgOnSwitchOut:3128` runs `damagecalc`. Nothing between `:3091` and `:3128` resets it: `MoveValuesCleanUp` (`:3621-3624`) is not in that script, and `HandleAction_UseMove`'s reset (`battle_util.c:92`) belongs to *move* actions, while `HandleAction_Switch` (`battle_util.c:294-310`) writes no `dmgMultiplier`.
* Port: `src/engine/factoryBattleScriptFullTurnDecision.ts:1793` `dmgMultiplier: 1` in `stageVoluntarySwitchRules`, and `:1726` starts execution at `BattleScript_PursuitSwitchDmgLoop`, **skipping `:3089-3094`** — so the `setbyte` never runs. The consumer is ported faithfully (`battleScriptHitChainOpcode.ts:1613` `damage = damage * rulesContext.critMultiplier * rulesContext.dmgMultiplier`), so the ×2 is simply absent. The interception branch itself is fully reachable (`factoryBattleScriptFullTurnDecision.ts:1628-1637`, no barrier).
* **Observable consequence:** whenever a Pursuit user intercepts a voluntary switch, the port deals **exactly half** the source damage — Pursuit's effective 80 BP becomes 40 BP. That changes the HP number, and therefore every downstream branch that reads it: whether the switching mon faints on the way out (which decides whether `BattleScript_SpikesOnAttackerFainted`/`getexp` runs at all), and the damage-variance draw's *consumer* even though the draw itself still happens.
* **Fixture that exposes it on the stock ROM** (`mechanicLab`, `overrides.parties`): player slot 0 a bulky Level-50 mon at full HP with no Pursuit weakness beyond neutral (e.g. Snorlax), player slots 1-2 anything legal; opponent slot 0 a fast Level-50 mon whose **only** move in all four slots is `MOVE_PURSUIT` (giving the Factory AI one legal choice without injecting a decision), opponent slots 1-2 anything legal. Nested trace: on turn 1 the player opens the party menu and switches slot 0 → slot 1. The ROM runs the real interception; compare the player's post-switch HP against the port. Source will show ~2× the port's damage.

**D2 — `protectUses` survives the switch (medium).**
* Source: `battle_main.c:3206-3208` memsets the **whole** `struct DisableStruct` for the incoming battler; `protectUses` is a member (`include/battle.h:75`), so it is zeroed.
* Port: `src/engine/battleScriptSwitchinOpcode.ts:495-553` rebuilds the battler by spreading `...candidate` and overriding an explicit list of fields (`:526-552`). `protectUses` is **not** in that list, and it *is* a modeled per-battler field (`battleScriptRulesContext.ts:351-352`), so the incoming mon inherits the outgoing mon's counter.
* The **battle-mechanics** half is self-healing and therefore *not* the consequence: `Cmd_setprotectlike` forces `protectUses = 0` whenever `gLastResultingMoves[attacker]` is not Protect/Detect/Endure (`battle_script_commands.c:6506-6509`), and §3 C24 clears `gLastResultingMoves` for the incoming battler — the port reproduces both (`battleScriptProtectlikeOpcode.ts:91`, `battleScriptSwitchinOpcode.ts:609`).
* **Observable consequence — the AI's RNG stream.** `AI_CV_Protect4` (`data/battle_ai_scripts.s:1921-1927`) reads `get_protect_count AI_USER` with **no** last-move guard: `if_equal 0, AI_CV_Protect_End` — otherwise `score -1`, then `if_random_less_than 128` (an extra `Random()` draw), then possibly another `score -1`. The port ports this exactly at `factoryAiCheckViability.ts:1309-1316`, including the extra draw at `:1311`. So if the Factory AI switches in a mon while its predecessor's `protectUses` was nonzero, and the new mon then evaluates a Protect/Detect move, the port takes the gated branch and **draws one `Random()` that the ROM never draws** — desynchronising every subsequent AI draw in that decision and, transitively, every RNG consumer for the rest of the battle.
* **Fixture:** opponent slot 0 = a Level-50 mon holding `MOVE_PROTECT` in all four slots; opponent slot 1 = a Level-50 mon whose slot 0 is `MOVE_PROTECT` and whose remaining slots give the AI a genuine choice; player slots ordinary. Trace: let the AI Protect on turns 1-2 (driving `protectUses` to 2), then force a switch — Roar the opponent out with a player `MOVE_ROAR` on turn 3 (`EFFECT_ROAR` hands into the same `switchindataupdate`, §5a R13) — and on turn 4 compare the AI's chosen move / the post-decision RNG cursor. Source starts the new mon at `protectUses = 0` (one `AI_CV_Protect` draw); the port starts it at 2 (two draws).
* Adjacent, **outside this audit's scope** (flagged, not claimed): `AI_CV_Protect`'s *first* rung `get_protect_count AI_USER; if_more_than 1, AI_CV_Protect_ScoreDown2` (`data/battle_ai_scripts.s:1895-1896`) also reads `protectUses`, and the port's early-exit block (`factoryAiCheckViability.ts:1274-1287`) has no `protectUses > 1` test at all. That is a pre-existing AI-porting gap, not a switch-lifecycle one.

### DIVERGENT-BENIGN notes

* **N1 (§3 C38).** The port's `switchindataupdate` additionally zeroes four `ProtectStruct` fields — `usedDisabledMove` (`:544`), `usedTauntedMove` (`:546`), `usedImprisonedMove` (`:547`), `notFirstStrike` (`:551`) — which `SwitchInClearSetData` never touches (`gProtectStructs` is cleared by `FaintClearSetData` instead, `battle_main.c:3292-3310`). Benign in singles because `TurnValuesCleanUp` memsets `gProtectStructs` every turn and a voluntary switch is always the turn's *first* action (§1 T1), so all four are already 0 when the switch runs. It would become live only if a Baton Pass or Roar mid-move could switch a battler that had already set one of these flags this turn — worth re-checking if the port ever models `WasUnableToUseMove` (`battle_util.c:890-899`) across a forced switch.
* **N2 (§4 E13).** `gActionsByTurnOrder[i] = B_ACTION_CANCEL_PARTNER` for the switched-in battler's turn slot (`battle_script_commands.c:5270-5274`) has no port site. Benign because the only reader in the ported scope is `ENDTURN_ORDER`'s bubble sort skip test — and that sort is already finding-1 of yesterday's audit (`docs/end-turn-ordering-audit-2026-08-25.md` §2 F1: the port never re-sorts at all), so this write currently has no consumer to be wrong for. It must be added *with* that fix, not before it.
* **N3 (§6 M5).** `rolloutTimerStartValues[battler]` is not zeroed by the port's switch-in. Benign because the field is write-only in the port: written at `battleScriptRolloutOpcode.ts:91-97` and `:117`, read nowhere in `src/` (whole-tree grep), with the damage escalation deriving from `ROLLOUT_HIT_COUNT - rolloutTimer` at `:98` instead. Fold it into D2's fix so it does not become live if a reader is ever added.
