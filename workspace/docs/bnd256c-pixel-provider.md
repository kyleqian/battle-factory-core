# bnd256c: sprite pixels leave the headless graph (finish plan Phase 3, bundle hygiene `bnd-c`)

Goal: `@pokebench/factory/headless` (`replayChallenge`) carries no battle sprite pixels. The 11.8 MB `assets-sprites` chunk
(`battle-back-sprites.json` + `battle-opponent-front-sprites.json`) was kept only by `battleCommandFieldArt.ts` (`speciesPic`).
bnd254b already moved every tick-path read to the small geometry / palette tables; this step makes the remaining pixel reads lazy
and removes the JSON import from the headless graph.

## What changed

- `src/engine/monPicPixels.ts` (no JSON): `installMonPicPixels({back, front})`, `monPicPixelsInstalled()`, `backPixels(sym)` /
  `frontPixels(sym)`; the last two throw `mon pic pixels not installed` before an install.
- `src/engine/monPicPixelsInstall.ts`: imports the two sprite JSONs and installs them at module top level. Static side-effect
  import (supervisor decision: no dynamic `import()`, so the browser mount keeps its synchronous first draw / `ready` timing).
- `battleCommandFieldArt.ts`: no sprite JSON import. `speciesPic` builds a frozen `pic` with `palette` from
  `battle-sprite-palettes.json` and enumerable lazy getters `tileset` (and `frame2` for the opponent side) that read the provider.
  The transform branch builds `{ get tileset() { return shown.pic.tileset; }, palette }`, so a tick-path view never reads pixels.
  (Defined with `Object.defineProperty`: an object spread would evaluate a getter at once.)
- Install points: `src/lib.ts` (static import), `tests/setup/monPicPixels.ts` (registered in `vite.config.ts` `setupFiles`, so
  `vitest.gate.config.ts` inherits it), every `tools/` file that imports `render` from `core.ts` (179) or the battleScene renderers /
  `battleResolutionPresentationRender` (111, incl. `tools/soak/randomRoundSoakDriver.ts`, the `--render-every` path). `play:random`
  and `tools/browser/*` drive the built page, which is covered by `lib.ts`. `tools/compare/appTrace.ts` installs through a guarded
  dynamic import that tolerates only a missing module, so `app-differential --harness-from-head` can overlay it on a base checkout
  from before this step.
- Side effects of editing tools: six retained framebuffer verifiers (`fire-blast`, `hail`, `heal-bell`, `psybeam` x2, `rock-blast`
  `*Framebuffer.ts`) have their sha256 pinned in `tools/compare/fixtures/*-evidence.json` (and `fireBlast`'s fixture sha in
  `tests/animation/dragonFireProjectileTrack.test.ts`); those pins were re-computed after the one-line import (their tests re-run the
  verifiers and still report the same exact-row counts). `sandTombSourceAudit.ts` only reads source text and was left untouched. Six
  `contain209*` / `contain213*` tests call `vi.resetModules()` and re-import `core.ts`; they now also re-import the install module.
- `headless.ts` does not import the install module (pinned by `tests/bnd256cPixelProvider.test.ts`). `battleScene.ts`,
  `monPicRender.ts` and `summaryInfoPage.ts` still import the JSON statically; Rollup tree-shakes them out of the headless build
  (confirmed below), so they stay for `bnd-d`.

## Proof

- Built-headless replay (`node --input-type=module` importing `dist-lib/headless.js`, four real-battle traces generated by the soak
  `RandomPlayer`: win + retire seed 1, loss seed 0, two wins `gameplaySeed 7`, one win Scene ON `gameplaySeed 42`): `frames`, `streak`, `ended`,
  `battles` and `digest` are identical before and after (digests `6dfdeb88acbb5d01`, `854ad54a31a0af3a`, `d07cde1f034d2876`,
  `b217d85f3168bd89`) and no "not installed" error. Only `ENGINE_BUILD` differs.
- `npm run compare:differential -- <38 traces> --base 33d93e25c --harness-from-head`: 7,561 / 7,561 captures byte-identical (draft menu /
  cursor / slot 6, Kabuto and other opponent front sprites with `frame2`, send-outs, doubleteam clone anim, summary Magby front animation,
  Scene ON and OFF battles). No committed trace stages a Substitute doll, CASTFORM or a Transform user; those renders are pinned by
  `tests/doll90DollCells`, `cast83CastformForms`, `trf174Transform` and the live Substitute tests, which pass through the real pixel path.
- `tests/bnd256cPixelProvider.test.ts`: provider throws before install and returns the JSON objects by identity after; building plain /
  transformed / doll field art views reads no pixels (spy tables); an uninstalled view still builds and only the pixel read throws; static
  ratchets (`battleCommandFieldArt.ts` has no sprite JSON name, the headless source graph never reaches the install module, `lib.ts`
  imports it, the built headless output has no sprite chunk).
