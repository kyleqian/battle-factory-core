### 1c. Swap-screen / carry-state / round-chaining — checked, **no change needed**

- **Swap-screen copy** (`battle_factory_screen.c:2350-2361` `CopySwappedMonData`, retail struct `struct RentalMon` at `include/global.h:357-363` has `u8 ivs` — a **scalar**, not six fields — this is retail's real save-data shape). TS equivalent: `applyFactorySwapMutation` (`src/engine/factorySwap.ts:201-231`). It spreads the whole `enemyParty[enemyMonId]` object into the player slot (full `BattleMon`-derived stats travel with the swap, matching `gPlayerParty[x] = gEnemyParty[y]`'s wholesale struct copy) and separately copies only the scalar `offered.ivs` (ATK IV) into the bookkeeping roster (`rentalMons[state.playerMonId] = {..., ivs: offered.ivs, ...}`, line 219-224) — this exactly matches retail's `rentalMons[...].ivs = ...ivs` single-byte copy. `FactoryRentalMon.ivs: number` (`factorySwap.ts:18`) and the roster↔record adapters (`factorySwapPresentation.ts:319` `ivs: record.fixedIv`, `:372` `fixedIv: record.ivs`) are correctly scalar-only and need **no change** — retail itself never stores more than the ATK IV in this bookkeeping struct.
- **Round-chaining / carry state**: `generateFactoryChallengeDraft` (`src/engine/factoryRoundChaining.ts:93-107`) calls `generateInitialFactoryRentals` fresh each challenge — no stored-record rebuild, so nothing to break here; §3 has the full call chain.
- **`healFactoryKernelParty`** (`src/engine/battleScenario.ts:180-229`) validates `currentMember.ivs.attack !== records[index]!.fixedIv` (line 192) when reconciling a live kernel party against its saved record. This check is scalar-only (ATK IV vs `fixedIv`) and stays correct under a random spread **as long as construction always sets `fixedIv = ivs.attack`** (commit 1's stated invariant) — no change needed, but this is exactly the kind of site that would silently produce wrong results if that invariant is violated (see §5).

### 1d. Draft-preview stat display — a real open question, not settled by ISSUES' text

`ANCHOR_DRAFT_RENTAL_RECORDS` (`src/engine/factoryDraftScreen.ts:756-769`) **throws today** if a canonical anchor rental's `ivs` are non-uniform (line 759-761) — harmless now (anchor is always challenge 0, `fixedIv=3`), but documents that the draft-screen path assumes uniform IVs structurally. The live preview path (`createFactoryRentalPresentation`, `src/engine/factoryRentalPresentation.ts:154` → `createFactoryCorpusPartyMember`) will automatically pick up real six-IV stats once §1a's `createFactoryCorpusPartyMember` change lands — **but check retail's actual behavior first**: `CreateFactorySelectableMons` (`battle_factory_screen.c:1740-1774`) calls `GetFactoryMonFixedIV` directly into `CreateMonWithEVSpreadNatureOTID` for the **draft-time preview** (so retail's preview DOES show a genuine random spread for a row-8 mon). But `SetPlayerAndOpponentParties` (`battle_factory.c:410-475`), which rebuilds `gPlayerParty`/`gEnemyParty` from the saved roster **at the start of every subsequent battle in the round**, reads only the stored scalar `rentalMons[i].ivs` (an ATK-IV byte, always `< 32`) and calls plain `CreateMon(..., ivs, ...)` — which **cannot** re-trigger `CreateBoxMon`'s random branch (only reachable for `ivs >= USE_RANDOM_IVS(32)`), so it silently collapses to a **uniform** ATK-IV spread for every stat, every battle after the first. No fixture/trace in this repo pins stats for a challenge ≥ 7 draft (`rg` found none — the only IV-derived-stat pins are uniform, `tests/factoryRentalGeneration.test.ts:239-244`). **Decision needed before landing**: does commit 2 model retail's two-stage divergence (random six-IV preview → uniform-ATK-IV battle party), or intentionally simplify to "six-IV everywhere `ivs` is present"? The latter is simpler and still `fixedIv == ivs.attack`-consistent, but is not byte-faithful to retail's `SetPlayerAndOpponentParties` rebuild. Flagged, not resolved — no oracle trace exists at this streak depth to settle it empirically (Battle Scene OFF oracle has no canonical snapshot past the anchor).

`--start-carry 42` starts a round at challengeNum 6 (streak 42). **Next throw once challengeNum 8 succeeds** (checked both routes):
- **Rental route** (this seed): if the challengeNum-8 round is *also* won, the next draft is challengeNum 9. `getLevel50InitialRentalFixedIv` (`factoryRentalGeneration.ts:193-209`) has **no** `>8`-clamps-to-row-7 branch today — only `ivIndex < DECLARED_FIXED_IV_ROWS(8)` is handled, so `ivIndex=9` (or 10 with better-range) falls straight to the same `throw new Error("initial-rental fixed IV is undefined for challenge 9")`. **This must be fixed in the same commit** or the port merely moves the crash one challenge deeper instead of removing it. `getLevel50FactoryBrainFixedIv` (`factoryBrainOpponentGeneration.ts:178-180`) already has this clamp (`ivArg > FIXED_IV_TABLE_LENGTH` → row 7) — mirror that shape into the rental and opponent functions.
- **Brain route** (different, per the brief's instruction to check both): Brain triggers at `challengeNum + 2 == 8` → `challengeNum == 6`, i.e. a round starting at **streak 42** (carry 42) reaching its Brain battle (battle 7) directly — no double-win needed. This is actually the *first* OOB argument-8 hit reachable from `--start-carry 42`, structurally independent of the rental crash above (different call site, `factoryBrainOpponentGeneration.ts:215`). Not confirmed empirically this session (the one seed run above happened to hit the rental throw first, at "b7 t6" — plausibly *inside* the Brain battle's tick, since battle 7 of a round is the Brain battle; the printed message text is unambiguously the rental-generation string, so this specific seed's proximate crash is the rental-side one, not the Brain one — but a smaller `--start-carry` sweep could hit the Brain throw as challengeNum 6's *own* Brain battle before any second win).
