# abs1: does holding / pressing A or B speed text up on the ROM, and does the engine differ?

Answer: **at the oracle save's text speed (FAST) the ROM speeds no surface up**; holding or mashing A leaves every glyph on its frame, and the
engine already printed the same. What did differ is the frame a mashed press is first *taken* after the last glyph (the page / message waits);
that is ported for the two surfaces measured (below). Method: the source table (section 1), then ROM-vs-engine first / last glyph bursts on
hold-A / mash-A traces (section 2), then press-gate scans k frames after the last glyph (section 3).

## 1. Source table: surface -> flag -> effect (reference/pokeemerald, pinned 83df84e40)

The speed-up is one branch, `RenderText` (text.c:947-953): `if (delayCounter && textSpeed) { delayCounter--; if (canABSpeedUpPrint && JOY_NEW(A|B))
{ hasPrintBeenSpedUp = TRUE; delayCounter = 0; } }`, plus text.c:944 (`JOY_HELD(A|B) && hasPrintBeenSpedUp` zeroes the delay for the rest of the print).
`AddTextPrinter` does `--textSpeed` and stores `textSpeed = 0` for speed 0 / TEXT_SKIP_DRAW (text.c:292-301). `GetPlayerTextSpeedDelay` returns
SLOW 8 / MID 4 / FAST 1 (menu.c:77-81, 480-487), so **FAST gives textSpeed 0 and the branch is never entered**: A / B cannot speed any print.
The oracle save's option is FAST (RAM-confirmed in the earlier timing docs), and the engine models only FAST.

| surface | flag set by | text speed | A / B speeds the print? |
|---|---|---|---|
| battle messages, B_WIN_MSG (both scenes) | battle_message.c:3016 `canABSpeedUpPrint = 1` (non-link, non-recorded: `GetPlayerTextSpeedDelay`) | FAST = 1 -> 0 | flag yes, **no effect at FAST** (SLOW / MID would) |
| other battle windows (`textInfo[windowId].speed`) | battle_message.c:3021 `= 0` | per window | no |
| Lobby attendant, PreBattleRoom briefing, BattleRoom opponent / escort / Noland boxes, postwin and terminal boxes (field `msgbox`) | field_message_box.c:127 `StartDrawFieldMessage` -> `AddTextPrinterForMessage(TRUE)` | FAST | flag yes, **no effect at FAST** |
| `ShowFieldAutoScrollMessage` (the Lobby save's "saving" line) | field_message_box.c:91-98 -> `AddTextPrinterForMessage(FALSE)` | auto-scroll 3 | no |
| battle party menu messages | party_menu.c:2569 `= TRUE` | FAST | flag yes, no effect at FAST |
| draft / swap / summary screen text | none (battle_factory_screen.c: `AddTextPrinterParameterized(..., speed 0)`) | 0 = drawn at once | no printer to speed up |
| player text speed at the oracle save | `optionsTextSpeed` | FAST (delay 1) | - |

Page waits are separate: `TextPrinterWaitWithDownArrow` (`\p` / `\l`) takes `JOY_NEW(A|B)` plus SE_SELECT whatever the flag says, and a `msgbox`
message end is `waitmessage` + `waitbuttonpress` (`WaitForAorBPress`). Those are press *gates*, not print speed (section 3).

## 3. What did differ: the frame a press is first taken (fixed)

Scans: the same trace with one 2-frame A press k frames after the last glyph L of a print (press first frame L+k; only the first frame is a new
press), ROM vs engine over 71-91 frames per k. Before the fix the engine took a press earlier or later than the ROM on two surfaces, so a player
who mashes A reached the next phase on a different frame (and the VBlank RNG cursor of everything after moved).

| surface | ROM takes the first press at | engine before | engine now |
|---|---|---|---|
| BattleRoom opponent intro box (canonical route, `msgbox` end) | L+3 (A at 738..740 ignored, 741 taken) | L+0 (k = 0 closed it) | L+3 (`MSGBOX_ACCEPT_ELAPSED = 3`, battleRoom.ts; Battle 2's box keeps its gate of 2, `JENSON_MSGBOX_ACCEPT_ELAPSED`, not re-measured) |
| Lobby attendant `\p` / `\l` page wait | L | L+1 | L (`attendantAcceptsInput`, factoryLobbyAttendant.ts) |
| Lobby attendant message end (waitbuttonpress) | L+2 | L+1 | L+2 |

After: room scan k = 0..7 (the box is not closed for k <= 2, closed at k = 3 on both sides, the box's own closing frames identical), Lobby `\p`
scan k = -3..3 (91/91 on all but k = -2) and end-page scan k = -2..5 (71/71 on all eight).

Not changed here, measured by earlier steps and left alone: the escort box (L+3, noland-room-scenes), the scouting pages (L+3, sct1), the postwin
recorded message (L+2, `POSTWIN_RECORDED_INPUT_READY_DELAY`), Noland's speech pages. **Not scanned by abs1**: the loss terminal's pages, the
PreBattleRoom briefing pages, the swap offer dialogue; any difference there is open.

## 4. Residuals (not fixed)

- Odd-k transition phase after the room box closes: the ROM starts the walk after the box on an odd absolute frame (k = 3: 773, k = 4: 775, k = 5:
  775, k = 6: 777; i.e. the first odd frame >= press + 32), the engine on press + 33. Equal for even press offsets (the canonical route's press is
  one), 1 frame late for odd ones. Visible in abs1-room-intro-mash (125/152 after, first diff 825). A frame-parity rule of the ROM's script,
  not a text rule.
- Lobby `\p` scan k = -2: one frame (5212, 1513 px) where the ROM shows the box blank for a frame the engine does not; it was the same before the
  change. Lobby mash also has one differing frame at 5244 (948 px).
- abs1-draft-mash: the SUMMARY open / close fade is 2 frames longer on the engine; not text.
- Pre-existing, unrelated: the ON battle animation (38/229 on hcr2-tackle-plr-on) and obr251-opponent-faint-off from 711.
