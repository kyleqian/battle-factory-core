## 1. The shared engine seam: `battleMovePower` on the request (Magnitude, Reversal, Flail, Endeavor)

ROM: `Cmd_attackanimation` (`battle_script_commands.c:1787`) emits **`gBattleMovePower`**, not the table power and not `gDynamicBasePower`. `gBattleMovePower` is written only by `CalculateBaseDamage` (`pokemon.c:3119-3122` = `powerOverride ? powerOverride : move power`, then Mud/Water Sport halving `:3216-3218` and the pinch-ability x1.5 `:3220-3226`). `gAnimMovePower` (what the scripts read: `battle_anim_mon_movement.c:975`, `battle_anim_ground.c:737`) is set from it in the controller (`battle_controller_player.c:2475`).
Measured (`prep10-analysis.json` `powerEquality`): at every activation of Magnitude, Reversal and Flail, `gAnimMovePower == gBattleMovePower == gDynamicBasePower` (15/15 bodies); for Endeavor `gAnimMovePower` equals whatever was left (`0` at battle start, `75` after Rock Slide, `prep10-probes/stage-r1/endeavor-*.json`).

Engine today: `src/engine/battleScriptHitChainOpcode.ts:2285` emits `String(moveRow.power)` (the static table power: route probe shows `179,0,1`, `175,0,1`, `222,0,1`, `283,0,1`). The engine's analogue of `gBattleMovePower` is the local `movePower` in `damageCalc.ts:386-395` (after the pinch boost; the sport halving is `battleScriptHitChainOpcode.ts:1521-1535`), which is never stored.
**Recipe (presentation-only, no damage/RNG touch):**
1. `src/engine/damageCalc.ts` (`calculateBaseDamage`, :292): also expose the final `movePower` (a new exported sibling `calculateBasePower`, or return `{damage, movePower}` through one call site) -- the value, not a new computation.
2. `src/engine/battleScriptRulesContext.ts` (`BattleScriptRulesContext`, near :714): add `battleMovePower: number` (init 0); write it in `damagecalcOpcodeHandler` (`battleScriptHitChainOpcode.ts:1602`) and the other `CalculateBaseDamage` callers (`Cmd_stockpiletobasedamage`, confusion self-hit `battle_util.c:2173/4023` = power 40, Future Sight `:8941`). Nothing reads it for gameplay.
3. `battleScriptHitChainOpcode.ts:2285`: emit `String(rulesContext.battleMovePower)` instead of `String(moveRow.power)`. Check existing consumers of `request.power` first (`battleMoveAnimation.ts:7,23-29`; the staged Rock Slide / Endeavor shake pins use their own constants, `battleScene.ts:8729-8800`); for a non-dynamic, unmodified move the value is identical to the table power.
4. **Persistence:** `gBattleMovePower` is EWRAM, zeroed only at power-on, so the register must survive across the battles of a run (orchestrator state), `0` at the first battle. Measured: 0 across the whole AI turn of the staged runs (3400 frames, no write before the first damage calc, `powerChanges` in the receipts), so the AI scoring path did not write it there; a trainer with a damage-scoring AI flag was not exercised (open question 2).
Test: unit pin `power == 20/40/80/100/150/200` through the Flail/Reversal hit chains at the HP bands of `mechanic-flail-hp-bands-off` / `mechanic-reversal-hp-bands-off` (`tools/integration/fixtures/prep10-analysis.json`), and `110`/`70` for the two Magnitude branches; then `liveMoveAnimation` adapter tests per move with the drafted fixtures.
Why presentation-only: the register is written from values the calculation already computed, read only at the MOVE_ANIMATION event.
